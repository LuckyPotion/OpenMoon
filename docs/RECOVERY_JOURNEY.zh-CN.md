# OpenMoon 的恢复历程

我们原本想把 Moon 从混淆后的材料里一点点恢复出来，做成一个能读、能改、能构建的客户端源码仓库。走到这里，花时间最多的并不是给类换个名字，而是证明每次修改仍然保留了原来的调用、初始化顺序和异常处理。

一开始拿到的不是一份能够导入 IDE 的工程。普通 Java、类生成配方、受保护依赖和运行材料散在不同批次里。反编译出来的代码可以帮助理解，却经常不能直接编译：有些 JVM 方法同名同参数，只靠返回值区分；有些控制流不能直接写成 Java；构造器会在 super 初始化之前计算参数；异常表也不总能用一层 try/catch 表达。

于是我们把“能看见源码”和“源码能重新生成实现”分开记账。正式恢复材料覆盖了 4093 个类身份、23419 个字段和 47105 个 Code 属性。早期构建仍是 673 份普通源码重新编译、3420 个接受归档复用；这个结果帮助保存了材料，却不是最终想交付的源码仓库。

还有一个很具体的障碍：Windows 文件名不区分大小写，原工程却有 1110 组名字在忽略大小写后冲突，涉及 2697 个类。直接解压会丢失身份。现在源码存放在独立身份目录里，构建用清单和精确 ZIP 条目交给编译器，输出也直接写入保留大小写的 JAR。

过程中有过看似通过、后来必须撤回的结果。九类组合包曾得到相同的 class 哈希，复审却查出工具 classpath 仍含旧 Stage，实现来源和输入锁不够干净。那轮被排除，修改供给边界后才重新构建、审查。37 类 S/R 运行影像也保留了原有差异；局部初始化成功，没有被写成整个客户端成功。

我们也在工具协作上走过弯路：模型名写错、通道 503、空回复和余额中断，都拖慢过进度。子代理恢复后，机械盘点、资源分卷交给 Luna，复杂泛型、调用与适配器修复交给 6.1-sol，主代理顺序集成。失败记录没有删掉，空任务也没有算完成。

后来，用户问了最关键的一句：这些工作究竟什么时候能变成一个可构建的客户端源码仓库。这个问题把路线重新拉回交付本身。当前工程明确选入 4097 个 Java 单元，覆盖 4093 个原类身份；旧接受 class 不再供应 owned 实现。返回值重载、构造器、异常区域、动态调用、枚举与桥接方法，都用可读源码和有来源的适配规则参与新构建。

编译错误曾以万计。许多表面上不同的错误，实际上来自少数共性问题：缺失导入、泛型擦除、参数重命名误伤字段、包名被同名类型遮蔽、转换器漏掉原桥接方法、调用选错返回值。集中修复以后，类型错误逐步清零。我们随后发现普通 javac 会在前序错误后跳过部分检查；完整流程又暴露大量重复受检异常诊断。因此工程使用明确记录的 JDK17 JVM 异常前端，仅单列 JVM 允许的异常传播与 catch 可达性限制，保留原 throw/catch，并继续拒绝类型、赋值和返回值错误。它不是普通严格 Java 模式，构建说明必须如实写清。

资源发布也有实际限制。原资源包约 273 MB，其中一个 native 条目本身超过 GitHub 单文件限制。工程把原包按字节分成六份，用纯 Java17 工具逐份校验并恢复原 SHA，不需要重新取得密钥，也不把运行账号和 token 放进仓库。

在恢复接近收束的时候，我们看到了公开的 [StylesFoundation/Moon](https://github.com/StylesFoundation/Moon)。用户说：“还是快了我们一步。”这种失落很真实。OpenMoon 仍然选择保留自己独立恢复出来的工程和这段路，公开仓库只作为参考链接，没有复制它的源码来填补我们的工程。

这份记录不把构建成功写成所有功能已经验收。源码构建、原生运行环境和客户端功能是不同的事情：原保护启动层、部分接口命名合同和运行闭包仍需在交付状态中逐项说明；模块、渲染、联网与 Via 由用户人工验收。最后的构建命令、产物与实际限制以仓库构建状态为准。

留下这个仓库，也是留下那些曾经走不通的路，以及我们最终学会如何证明一份源码能够重新产生实现的过程。
